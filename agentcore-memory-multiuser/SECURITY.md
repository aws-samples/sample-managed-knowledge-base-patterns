# Security Policy
## Reporting a vulnerability
If you discover a potential security issue in this sample, we ask that you notify AWS/Amazon Security via our [vulnerability reporting page](https://aws.amazon.com/security/vulnerability-reporting/) or directly via email to aws-security@amazon.com.
Please do not create a public GitHub issue for a security vulnerability.
## The security properties this sample depends on
Read this before changing `backend/identity.py`, `backend/aws_sessions.py`, `Assistant.build_request` in `backend/assistant.py`, `app_role_policy`, `app_role_trust_policy` or `ensure_cognito` in `infra/setup.py`, or `infra/app-role-policy.json` and `infra/app-role-trust-policy.json`.
Amazon Bedrock Managed Knowledge Base provides ACL-aware filtering for the identity in `userContext`. Per the [AWS documentation](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-managed-acl.html), ACL awareness is filtering, not authorization: the application authenticates the user and passes verified identity context, and Bedrock applies document permissions for that identity. AgentCore Memory likewise scopes data by the `actorId` and namespace in the request. The consequences:
- `userContext.userId` is only the email of a verified Cognito ID token (`token_use: id`, `email_verified: true`), lowercased. The user pool makes `email` immutable and an alias, so a user cannot change it and two users cannot share it. The email is the join key against the document ACLs, so another identity provider must keep it unique, verified, and stable. If an email is reassigned to another person, that person inherits the previous user's document access.
- IAM does not constrain `userContext`. Any principal with `bedrock:Retrieve`, `bedrock:AgenticRetrieveStream`, or `bedrock:GetDocumentContent` on the knowledge base can send any email. The holders of those permissions are part of the ACL boundary; grant them only to the application role.
- `actorId` and `namespacePath` are only the token's `sub`, which is stable and never reused. `sessionId` is the one value the client supplies, and it is safe because short-term memory is keyed under `actorId`.
- The backend assumes the application role once per user with `RoleSessionName=user-<sub>`, `SourceIdentity=<sub>`, and the session tag `userId=<sub>`. The trust policy accepts only the backend's principal (`aws:PrincipalArn`), requires the tag and the `SourceIdentity` in Cognito `sub` form, and allows no other tag key. The memory statements compare `actorId` and `namespacePath` against the tag. The backend chooses the tag, so this guards against application code that mis-binds an identifier, not against the backend principal itself.
- The namespace condition is `/anycompany/${aws:PrincipalTag/userId}/*`. Do not drop the `/` after the tag, which keeps one user's prefix from matching another's. An empty tag widened the earlier pattern without the `/` to every user's namespace; the trust policy now rejects an empty or malformed tag, so keep that check if you change the pattern.
- Memory outlives document access. Removing an email from an ACL does not remove conversation history or long-term records built from those documents. Delete them (`DeleteEvent`, `DeleteMemoryRecord`) as part of the access change if that matters to you.
## Failure behavior worth knowing
A missing or invalid token returns HTTP 401 with a correlation ID; the reason is logged on the server, not returned. A malformed AssumeRole is denied by the trust policy, and the turn ends with a generic error. Memory denials soft-fail: the answer still comes from the knowledge base, so a broken memory policy looks like missing personalization rather than an error, and a broken ACL looks like fewer results.
Confirm each layer instead of inferring it from the absence of errors. `scripts/abac_probe.py` exits non-zero when IAM allows a malformed AssumeRole or a mis-scoped memory call, and `scripts/e2e.py` checks document ACLs and per-user isolation through the running backend.
## Architectural boundary
Identity is derived in one place, `backend/identity.py`, and the request is built in one place, `Assistant.build_request`. Keep it that way: a second code path that sets `userContext`, `actorId`, or `namespacePath` doubles what has to be reviewed.
## Reporting scope
This is a sample intended to be read and adapted, not a supported product. Please still report security issues through the process above, because a defect copied out of a sample propagates.
